# AGENTS.md

Guidance for coding agents working in this repository. Read [README.md](README.md) for what
Jemmy is and [CONVENTIONS.md](CONVENTIONS.md) for naming and EDT rules before changing code.
[TODO.md](TODO.md), [PLAN.md](PLAN.md) and [TEST-COVERAGE-MAP.md](TEST-COVERAGE-MAP.md) record
the upstream-port history; update TEST-COVERAGE-MAP.md when you rename a test.

## Layout

| Source set | Contents |
|---|---|
| `src/main` | The library (`org.netbeans.jemmy.*`) |
| `src/testFixtures` | JUnit extensions and helpers shared by both suites and by consumers (`JemmyStateResetExtension`, `JemmyFailureDiagnosticsExtension`, `SaveScreenshotOnFailureExtension`, `TestWindows`, `OnQueue`, `LookAndFeelProvider`) |
| `src/test` | Unit tests (`test` task) |
| `src/userInterfaceTest` | Tests that open real Swing windows and drive them with the AWT Robot (`userInterfaceTest` task) |

## Toolchain

- **Java 8 target.** `build.gradle.kts` requests a Java 8 toolchain. CI pins **Temurin 8u345**.
  Gradle has no toolchain download repositories configured, so a JDK 8 must already be
  installed and discoverable, or passed explicitly (see below).
- **Gradle 9.7 via the wrapper.** Gradle 9 itself needs **Java 17+** to run, so a machine needs
  two JDKs: 8 for compiling and testing, 17+ for Gradle.
- **Wrapper scripts.** Use `gradlew.bat` on Windows and `./gradlew` on Linux or macOS. Both
  were generated by Gradle 9.7's `wrapper` task. If you upgrade Gradle, run
  `./gradlew wrapper --gradle-version <version>` and commit every file it changes, together:
  both scripts, `gradle/wrapper/gradle-wrapper.jar` and `gradle-wrapper.properties`.

- **Pointing Gradle at JDK 8** without touching the repo, use one of:
  - `-Porg.gradle.java.installations.paths=/path/to/jdk8`
  - `-Porg.gradle.java.installations.fromEnv=JAVA_HOME_8_X64` (what CI uses), plus
    `-Porg.gradle.java.installations.auto-detect=false` so a different JDK 8 can't win.

## Tasks

| Task | What it does |
|---|---|
| `compileAll` | Compiles every source set |
| `test` | Unit tests |
| `userInterfaceTest` | UI tests, one JVM, sequential (`maxParallelForks = 1`) |
| `checkLicenseHeaders` | Fails if a `.java` file under `src/` lacks the GPLv2 + Classpath header in its first 20 lines |
| `check` | All of the above |

Use `--continue` with `check` so a failing unit suite doesn't hide the UI suite's results.

## Test properties

The test tasks forward these from `-D...` or `-P...` on the Gradle command line into the test
JVMs (`forwardTestProperties()` in `build.gradle.kts`):

| Property | Effect |
|---|---|
| `swing.defaultlaf` | Look and feel for the test JVM. Defaults to the native one: `WindowsLookAndFeel` on Windows, `AquaLookAndFeel` on macOS, unset (Swing's Metal) elsewhere |
| `jemmy.diagnostics.enabled` | `false` turns off Jemmy's failure diagnostics: the Markdown diagnostics report and EDT-failure recording. Failure screenshots have their own opt-out, the `@NoSaveScreenshotOnFailure` tag. The old name `jemmyDiagnosticsEnable` is no longer read |
| `jemmy.testing.window.x`, `jemmy.testing.window.y` | Where `TestWindows.place` puts test windows (default 300, 300) |

### Look and feel pitfalls

- With no `swing.defaultlaf`, Swing uses **Metal on every OS**, not the native look and feel.
  The build sets the native one explicitly for that reason.
- A look and feel class that can't load on the platform (e.g. `WindowsLookAndFeel` on Linux)
  breaks Swing for the whole JVM. `UIManager` marks itself initialized *before* loading the
  default, so only the first caller sees `Error: Cannot load ...`; after that
  `UIManager.getLookAndFeel()` returns `null`. `org.netbeans.jemmy.util.LookAndFeel` turns that
  `null` into an `IllegalStateException` naming `swing.defaultlaf`. If every UI test class fails
  in `JemmyStateResetExtension.beforeAll`, check this first.
- Tests that switch look and feel must restore the previous one in `finally`
  (see `LookAndFeelTest`, `InternalFrameTitleButtonsLafTest`).

## Writing UI tests

- Register `@ExtendWith(JemmyStateResetExtension.class)` on every UI test class. The suite runs
  in one JVM, and this extension resets process-wide state (look and feel, tooltips, drivers,
  timeouts, event queue) between classes.
- Follow CONVENTIONS.md: touch raw components only on the EDT, and use `of(...)`, `waitFor(...)`
  and `find...(...)` for what they promise.
- **Don't depend on the machine or the checkout.** The first Windows CI run found tests that
  passed on a developer machine but failed on the runner:
  - `JFileChooser` hides whatever the desktop hides (the `awt.file.showHiddenFiles` desktop
    property on Windows, dot-files on Linux), and Git for Windows marks `.git` hidden. If a
    test compares the chooser with `File.listFiles()`, call `setFileHidingEnabled(false)`.
  - CI checks the repo out to `D:\a\jemmy-merge-prep\jemmy-merge-prep`, where the parent has
    the same name as the checkout. `JFileChooserOperator.selectPathDirectory` matches by name
    and prefers the deepest entry. Build directory fixtures under `@TempDir` with unique names
    instead of using `user.dir` or its parents.
- Failure screenshots (`.png`) and diagnostic reports (`.md`, `.zip`) are published as JUnit
  file attachments, which land under `build/junit-jupiter/<test class>/<test method>/`.

## CI

`.github/workflows/windows-ui-tests.yml` runs `gradlew.bat check --continue` on
`windows-latest` for pushes to `main`, for pull requests, and manually. It:

- installs Temurin 8u345 and 21 with `actions/setup-java` (21 runs Gradle),
- uses `gradle/actions/setup-gradle` with `cache-provider: basic` (MIT-licensed; the action's
  default "enhanced" provider is proprietary),
- tries to raise the desktop to 1920×1080 (best effort),
- uploads `build/reports/`, `build/test-results/` and `build/junit-jupiter/` (screenshots and
  diagnostic reports) as the `windows-test-reports` artifact.

A manual (`workflow_dispatch`) run only works once the workflow file is on `main`; on a branch,
the dispatch API returns 404.

## Running UI tests on Linux (including Claude Code cloud sessions)

Cloud sessions are Linux containers, not Windows. They can run the build, but it isn't the
target platform:

- Install a JDK 8. For parity with CI, use Temurin 8u345
  (`OpenJDK8U-jdk_x64_linux_hotspot_8u345b01.tar.gz` from the `adoptium/temurin8-binaries`
  release `jdk8u345-b01`, checked against its `.sha256.txt`), then pass
  `-Porg.gradle.java.installations.paths=...`.
- Run under a virtual display:
  `xvfb-run -a -s "-screen 0 1920x1080x24" ./gradlew check --continue`.
- The unit suite passes. Expect some UI failures that don't reproduce on Windows. Xvfb has no
  window manager, so maximize/demaximize, window activation, focus-owner and owned-window tests
  fail, and some drag-and-drop and slider tests time out. Tests run under Metal, not the
  Windows look and feel. Treat Windows CI as the authority for UI results.
- The container is temporary: the JDK install and Gradle download don't survive into a new
  session.
